# Notebook 源码教练

把一个 `.ipynb` 文件同时作为课程、练习场和学习记录。教学必须落到用户给出的源码与问题上，并通过可运行的最小实验帮助用户建立可迁移的理解。

## 1. 取得 Notebook 路径

先从用户消息和当前上下文中寻找明确的 `.ipynb` 文件路径。

路径缺失时，只询问用户希望保存或继续使用的 `.ipynb` 路径，然后停止本轮工作。路径明确前不创建 Notebook，也不改用默认文件名。

完成标准：得到一个明确的 `.ipynb` 路径，并确认它是新建文件还是现有学习笔记。

## 2. 加载 Teach 教学方法

读取当前环境中已有 `teach` skill 的完整 `SKILL.md`，把它作为本轮教学设计的上游方法。优先使用 Agent 已知的 skill 位置；否则依次检查：

1. `~/.pi/agent/skills/teach/SKILL.md`
2. `~/.agents/skills/teach/SKILL.md`
3. 当前项目及其父目录中的 `.pi/skills/teach/SKILL.md` 或 `.agents/skills/teach/SKILL.md`

多个路径指向同一文件时只读取一次。没有找到时，向用户询问现有 `teach` skill 的路径，不凭记忆重建它。

应用 Teach 中的 mission、最近发展区、知识与技能、检索练习、间隔练习、反馈回路和高可信资源原则。代码教学的高可信资源优先取自当前项目的源码、测试和文档；只有用户明确要求或问题依赖最新信息时才检索外部资源。把 Teach 的存储模型映射到 Notebook：

- mission、偏好和当前水平写入 `teach-state` 单元
- learning records 写成该状态单元中的进度与误区
- lessons 写成本轮带 tag 的 Markdown 和代码单元
- references、resources 和练习材料直接写入相关 Notebook 单元
- 交互组件改为可执行代码单元及其输出

Teach 的教学方法是上游，当前 skill 的 Notebook 工作流是交付约束。所有教学产物与进度仍只进入用户指定的 `.ipynb`。

完成标准：已读取现有 Teach 原文；本轮采用的教学策略能对应到其中的具体原则；没有创建 Teach 默认的 HTML 或目录式工作区。

## 3. 建立源码证据

读取用户给出的源码上下文、相关定义、调用点和测试。以解决当前问题所需的最小范围为起点；遇到无法从局部代码解释的行为时，沿调用链继续读取。把项目源码、测试和项目文档作为首要证据，区分代码已证明的事实与教学推断。

现有 Notebook 也属于输入：解析其 cells、metadata 和 outputs，找到已有目标、已完成内容、用户作答、误区与待办。保留用户编写的单元、既有输出和未知 metadata。

信息不足以确定问题边界时，提出一个能解除阻塞的具体问题；否则直接制作教学内容。

完成标准：当前问题涉及的关键符号、执行路径和预期行为都有源码或测试依据；现有学习进度已纳入本次难度选择。

## 4. 设计一个紧凑教学回路

每次只讲一个能够在当前 Notebook 内验证的核心点。按用户现有水平组织以下回路，省略对当前问题没有帮助的部分：

1. **任务动机**：从用户问题或已有 Notebook 中确认为什么要掌握它；动机不明确且会影响教学方向时，先询问用户。
2. **目标**：用一句话写出学完后用户能解释、预测或修改什么。
3. **源码地图**：列出关键文件、符号和调用关系，使用仓库相对路径；只摘录支持讲解的最小代码片段。
4. **心智模型**：解释数据、控制流、状态或抽象边界如何运作，并明确回答用户的问题。
5. **先预测**：在运行关键实验前，让用户先写下预期结果及理由。
6. **最小实验**：用可执行代码单元直接导入、调用、观测或测试相关源码；让实验一次只改变一个关键条件。
7. **迁移练习**：给出一个与原问题结构相同但表面不同的小任务。答案放在后续独立单元中，并标记为解答，便于先作答再查看。
8. **检查点**：总结已掌握内容、仍不确定之处和最合适的下一步。

讲解优先使用具体运行轨迹、值的变化、断言和失败示例。代码单元应短小、可重复运行，并说明运行目录、内核、依赖和任何必要前置状态。源码默认为只读；实验使用临时数据、测试替身或项目已有测试入口。只有用户明确要求修改源码时，才把修改作为练习或实施任务。

完成标准：用户可以在 Notebook 中完成一次“预测 - 运行 - 解释 - 迁移”回路，且每个结论都能追溯到源码证据或实验结果。

## 5. 写入唯一的进度容器

交付物是用户指定的单个 `.ipynb` 文件。课程正文、练习、解答、引用和进度都写入其中，不创建 HTML、`lessons/`、`reference/`、`assets/`、学习记录或其他课程容器。

使用 `nbformat` 4。新建 Notebook 时设置合适的 `kernelspec` 与 `language_info`；无法可靠判断内核时采用最贴近源码且当前环境可用的内核，并在首个设置单元中说明假设。不要伪造执行输出。

维护一个带 `teach-state` tag 的 Markdown 单元作为可见进度状态。整个 Notebook 只保留一个该单元，并更新这些字段：

- 当前问题与学习目标
- 源码范围和关键符号
- 已完成的教学回路
- 用户已表现出的理解与误区
- 待验证项
- 下一步

为本轮新增单元添加同一个 `teach-lesson-NNNN` tag，其中编号按已有最大编号递增。为答案单元额外添加 `teach-solution` tag。追加新一轮内容，不覆写既有课程或用户作答；只原位更新 `teach-state` 单元。使用 JSON 感知的方式写入，保持单元顺序、未知字段和已有输出。

完成标准：路径处只有一个有效的 Notebook 交付物；状态单元唯一且已更新；本轮单元可与旧内容区分；用户内容和已有输出保持完整。

## 6. 验证

写入后重新解析 Notebook JSON，并检查：

- `nbformat` 为 4，所有单元类型与 source 结构有效
- `teach-state` 恰好一个，本轮 lesson tag 存在且编号未重复
- Markdown 中引用的源码路径存在，或明确标为用户提供的外部上下文
- 代码单元包含运行所需的最小前置说明，不含占位伪输出

当前环境具备对应内核且代码安全、可重复时，执行本轮代码单元或整个 Notebook，再检查错误输出和断言。可能写外部状态、调用生产服务、使用凭据或触发不可幂等行为的单元只做静态检查，并明确标注为未执行。执行 Notebook 时保留用户已有输出，除非用户明确要求全部重新运行。

完成标准：Notebook 可解析，结构检查全部通过；可安全执行的本轮实验已经运行成功，其他单元逐项记录未执行原因。

## 回复用户

简洁报告 Notebook 路径、本轮核心教学目标、是否实际执行、验证结果和下一步。教学正文保留在 Notebook 中。
