# GitHub Issue 实现调度

## 授权与范围

用户通过 `/implement` 明确要求实现 GitHub Issue 时，授权父 Agent 使用 Subagent 实现和审阅该任务及其子任务。仅查看、分析或制定计划不构成执行授权。

本文件提供默认策略；用户当前请求和项目明确约定可调整范围与分工，执行始终遵守宿主工具的权限、安全约束和资源限制。依赖关系不自动授权实现范围外的任务；未完成的范围外依赖须向用户确认。

## 1. 发现任务图

读取项目 AGENTS.md 指向的 Issue 操作约定，再读取主 Issue、子 Issue、相关评论与原生依赖；将正文中的显式依赖一并纳入。没有项目操作约定时，使用平台支持的接口。

完成条件：范围内每个可执行任务的规格、前置依赖和验收条件均明确，且无未解决的冲突或循环。信息不足时先向用户确认，不凭编号推断顺序。

## 2. 分配与调度

默认每个可执行的叶子 Issue 对应一个独立实现 Subagent；汇总 Issue 由父 Agent 管理。非叶子 Issue 若含独立实现工作，先确认其分工。合并或拆分实现分工须经用户同意。

启动前读取当前 Subagent 工具的工作流指南并发现可用代理。使用一个顶层异步工作流统一调度；子任务仅在该工作流内启动。并行写入使用独立 worktree，每个工作目录只设一个写入者。

资源允许时立即启动所有就绪任务，不等待无关任务。交接明确 Issue、规格、基线、改动范围、验收命令及持久化产物位置；子 Agent 负责自身任务，父 Agent 负责调度。按工具要求绑定产物位置，并在依赖关口消费结果。

完成条件：每个启动任务均有负责人、隔离工作目录、可追溯基线和验收要求；未启动任务有可解释的依赖或资源阻塞原因。

## 3. 验收与解锁

父 Agent 核验前置任务的提交、约定测试和独立审阅证据，再将已验收改动集成到后继任务基线。独立审阅使用新的上下文，范围遵循项目约定。

完成条件：后继任务的基线包含全部已验收前置改动；Subagent 的完成声明本身不构成解锁依据。任务验收失败时阻塞其后继，无关任务可继续。

调度、启动或子任务工具等基础设施失败时，停止受影响执行，报告确切错误、运行状态、仓库与 worktree/分支/基线，并核实工作目录是否干净或保存部分 diff。后续处理遵循宿主恢复协议；未经用户批准不切换执行协议或工具绕过。

## 4. 集成与交付

父 Agent 负责冲突处理和最终验收，遵循 `/implement` 的测试、审阅和提交要求。将任务改动集成并提交到发起任务时所在分支，保留用户原有改动。

完成条件：范围内全部任务通过验收，集成结果完成验证并提交；交付记录包含实际提交、测试与审阅证据、产物位置及残余风险。Issue 更新遵循项目操作约定，只记录已验证的结果。

默认不 push、不创建 PR。除规格冲突、权限问题、执行阻塞或调整任务分工外，无需逐任务请求确认。
